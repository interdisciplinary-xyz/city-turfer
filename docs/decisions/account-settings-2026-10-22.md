# Account settings: name, e-mail, optional password (contract 0.5.0)

On 2026-10-22 the founder asked to build the Account tab of
`docs/plans/account-settings-2026-10-22.md` with its recommendations. This record takes those
recommendations as decisions. It **narrows A1** of `docs/decisions/api-accounts-2026-10-22.md`:
e-mailed codes stay the default sign-in, and a Turfer may now _add_ a password.

## Decisions

| #   | Decision                      | Chosen                                                                                                                                                                                    | Rejected                                              |
| --- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| AC1 | Passwords                     | Optional, beside codes. Accounts are still created only by a code (`emailAndPassword.disableSignUp`). A forgotten password is "sign in with a code, then set a new one": no reset route   | passwords only; no passwords (A1 as it was)           |
| AC2 | Password rules                | 12–128 code points, any characters, not trimmed, no composition rules (NIST SP 800-63B); Better Auth's scrypt hash                                                                        | composition rules; 8-character minimum                |
| AC3 | Breached passwords            | Have I Been Pwned range API: only the first 5 hex characters of the SHA-1 leave the server (k-anonymity, `Add-Padding`); 1.5 s timeout, fails open; never logged. A fake in tests and dev | a bundled list (stale, large); no check               |
| AC4 | Step-up                       | A fresh code mailed to the **current** address before changing the e-mail, or setting, changing or removing the password                                                                  | current password (code-only accounts have none); none |
| AC5 | After e-mail/password changes | Every other session is revoked (phones and browsers); the one that made the change stays. A security mail goes to the old (or current) address                                            | keep sessions                                         |
| AC6 | Name                          | `users.display_name` is the one source (mirrored into `auth_users.name` in the same transaction). Rules in core `displayName()`: trimmed, NFC, ≤ 40 code points, no control characters    | name in `auth_users` only                             |
| AC7 | Staff                         | The admin portal may show "has password" and when it changed, never change a user's name, e-mail or password                                                                              | support-driven changes (account takeover path)        |
| AC8 | Web portal                    | The same flows in `/[locale]/account` are handed to the web-portal work (lane A); the routes below are what it codes against                                                              | building the web part here, in parallel with lane A   |

## Contract (additive; old clients keep working)

All routes need a signed-in **account** session; a device-token caller gets
`403 identity.account-required`. Field rules come from `@cityturfer/core/identity` (`displayName`,
`newEmail`, `newPassword`), so their error codes are the problem `code`s.

| Route                                 | Body → answer                                         | Errors                                                                                                           |
| ------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `GET /v1/me`                          | → `User` + `name`, `hasPassword`, `passwordChangedAt` | —                                                                                                                |
| `PATCH /v1/me`                        | `{ name: string }` (blank clears) → `200 User`        | `422 display-name.too-long`, `422 display-name.invalid`                                                          |
| `POST /v1/me/step-up/codes`           | `{}` → `202 {}` (mails a code to the current address) | `429 auth.rate-limited`                                                                                          |
| `POST /v1/me/email/codes`             | `{ newEmail, stepUpCode }` → `202 {}`                 | `401 auth.invalid-code`, `422 email.invalid`, `422 email.unchanged`, 429                                         |
| `POST /v1/me/email`                   | `{ newEmail, code }` → `200 User`                     | `401 auth.invalid-code`, `409 email.taken` (only after the new inbox's code proved ownership), 422 as above, 429 |
| `PUT /v1/me/password`                 | `{ newPassword, stepUpCode }` → `204`                 | `401 auth.invalid-code`, `422 password.too-short`, `422 password.too-long`, `422 password.breached`, 429         |
| `DELETE /v1/me/password`              | `{ stepUpCode }` → `204` (also without a password)    | `401 auth.invalid-code`, 429                                                                                     |
| `POST /v1/auth/sign-in` (second body) | `{ email, password }` → `200 Session`                 | `401 auth.invalid-credentials` (same for a wrong password, no password, or no account), 429                      |

- `User.displayName` stays (deprecated): `name ?? id`, for phones on older builds. New clients read
  `name` and show "You" when it is null.
- A step-up code is single use: `POST /v1/me/email/codes` spends it, the change-e-mail step then
  needs only the code from the new inbox. Codes: 6 digits, 10 minutes, 3 tries, A5's limits.
- `POST /v1/me/email/codes` answers 202 for a valid step-up code even when the new address belongs
  to another account (no enumeration); that inbox then gets a mail saying the address is in use.
- Password sign-in counts in the same failed-sign-in buckets as codes (A5).
- A taken address gets the "in use" mail and **no code**, so its confirm step answers 401 like any
  wrong code. `409 email.taken` is therefore reached only when the address was free when its code
  was mailed and another account took it before the confirm (the code proved the inbox).

## How it is built (api-engineer, 2026-10-22)

Choices the contract above leaves open; each is in `apps/api/src/identity/` with tests in
`apps/api/src/__tests__/account.test.ts`.

| Choice                            | Chosen                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Rejected                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Step-up and new-address codes     | Our own `OneTimeCodes` (`codes.ts`) over Better Auth's internal adapter: A1's rules (encrypted, reuse while valid, 3 tries; every write a compare-and-swap on the row read (id and value): the right code deletes exactly that row, a wrong one bumps its try count in place, so concurrent tries all count and a code issued meanwhile is never touched); keys `step-up-otp-<address>` and `email-change-otp-<user id>:<HMAC of the new address>` (no plain new address stored)                                                                                                                                                                                                                                                                                                                                                       | emailOTP's change-email flow (mails nothing for a taken address, writes only `auth_users`, revokes no session, wants a fresh cookie session); its `forget-password` type as step-up (wrong name, no single-use check); consume-then-recreate on a wrong try (emailOTP's pattern: a code issued in the gap is shadowed by the re-created row)                                   |
| Limits                            | Step-up codes in the current address's A5 code buckets, except their own one-a-minute bucket (`stepUpCodesPerEmailPerMinute`), so the first sensitive change right after a code sign-in works; the 3-per-10-minutes and daily caps stay shared, so the mail volume per address stays bounded. New-address codes in the **new** address's buckets (sign-in minute bucket included), checked before the step-up code is spent and counted when the mail goes out; accepted race: a concurrent request can fill the bucket between check and count, so the step-up code is spent and the answer is still 429 (rare; the user asks for a new code). | Order of checks                   | Field rules, then (for passwords) the failed-sign-in caps (peek), the breach-check cap and the breach check, then the step-up code: a refused name, address or password does not spend it, and a locked-out caller gets 429 without an outbound call. The name's schema cap is 1000 characters (body bound only), so any name over 40 gets the core's `422 display-name.too-long`                                                                                                                                                                                                                                                                                                                                                                                                                                                      | spending first                                                                                                                                                                                                                                                                                                                                                                 |
| Password storage                  | `emailAndPassword` on with `disableSignUp`; `auth.api.signInEmail` to sign in (it hashes when there is nothing to compare: about constant time); setting writes the scrypt hash into the `credential` row of `auth_accounts` ourselves, in one transaction with the session revocation; `passwordChangedAt` = that row's `updated_at`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | `auth.api.setPassword`/`changePassword` (need the current password or no password; no transaction with the revocation)                                                                                                                                                                                                                                                         |

## Privacy

No route logs a name, address, code, password or hash prefix. The breach check sends 5 hex
characters of a SHA-1 to `api.pwnedpasswords.com` with padding on; it is named in the privacy
policy. Passwords live hashed in `auth_accounts.password` and go with the account on `DELETE /v1/me`
(cascade). No migration: every column already exists.
