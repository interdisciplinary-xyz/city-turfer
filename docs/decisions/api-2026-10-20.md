# HTTP API (v0.8.0)

> **Partly superseded (2026-10-20):** the routes, upload body, paging, Home City paths, achievements
> and export are replaced by the sync-first contract in
> [`api-sync-2026-10-20.md`](api-sync-2026-10-20.md). Stack, hosting, phases and risks below still
> stand.

Asked for on 2026-10-20: "Lets start with current API routes. If we don't have API now we should
create a separate app called `api` in `apps/api`. Please consider current architecture and current
existing user and their data. We should actually extract current back-end logic to `apps/api` and
add swagger as a docs layer. This should be a part of preparation of architecture to deploy it to
Vercel." Servers may hold full GPS tracks, owned by the user (founder's choice, same day). How to
work on it: the `api-design` skill and the `api-engineer` agent. Code wins on conflict.

## Starting point

CityTurfer has no backend. The phone is the source of truth: one SQLite database per user, a mock
single account (`admin`), domain and application layers in `apps/mobile/src` that are plain
TypeScript. Studied on `scope/v0.8.0`:

- **Server-worthy use cases:** Activity Log (import, list, detail, rename, delete, track), Territory
  (claim, release, reclaim, viewport, summary, claim of an activity, Home City, city search),
  Achievements (pure evaluation), Identity (the `AuthGateway` port).
- **Device-only:** Recording (GPS sessions, background task) and Health Sync's HealthKit store.
  Their results reach a server as finished Activities.
- **Ids are stable client strings** (session UUIDs, `hk-…` for Apple Health imports), timestamps are
  epoch ms: the existing user's history can be uploaded with idempotent upserts.
- **Blocking a server today:** the `@/` alias, a few `@/constants` imports, `__DEV__` in the outbox,
  `DETAIL_ZOOM` in a Territory use case, SQLite-only SQL in the repositories, and no `user_id`
  anywhere (one database per user).

## Decision

- **`apps/api`** (`@cityturfer/api`): **Hono** on Vercel (zero-config Node function, region `fra1`),
  its own Vercel project with Root Directory `apps/api`.
- **Contract-first in code:** routes declared with **@hono/zod-openapi** and **zod 4**; the same
  schema validates requests, types handlers and produces an **OpenAPI 3.1** document.
  `apps/api/openapi.json` is generated (`pnpm --filter @cityturfer/api run openapi`), committed,
  checked for drift and linted with **Redocly** in `ci:quality`.
- **Docs:** **Swagger UI** at **https://cityturfer.local/swagger** (dev route of the website's
  server, like `/storybook`) and at `/swagger` on the API itself.
- **Routes are driving adapters:** parse → use case → DTO. No business rules in handlers. Every
  `/v1` route maps to an existing use case (table below).
- **Server data:** **Neon Postgres in Frankfurt** with **Drizzle**, `user_id` on every row;
  **PGlite** in tests. **Better Auth** later, behind the existing `AuthGateway` port.
- **Turf on the server is recomputed from uploaded tracks** (canonical order: activity start), not
  copied from the phone. Visit totals match the phone; "new turf" numbers may differ slightly.

## Phases (each a PR into the scope branch; mobile stays JS-identical and OTA-safe)

1. Skills, agent, tools: `api-design` skill, `api-engineer` agent, spec generation, drift check,
   Redocly lint in `ci:quality`.
2. `apps/api` skeleton: every route above declared with schemas and shown in Swagger; `/v1/health`
   live, the rest `501` with a problem+json body; `vercel.json` (`fra1`); the `/swagger` dev route.
3. **packages/core** (`@cityturfer/core`): shared kernel, core constants, each context's domain +
   application + contract, outbox and `H3CellGrid` (`@cityturfer/core/h3`). One context at a time,
   with re-export shims in the app. Prep: relative imports instead of `@/`, `DETAIL_ZOOM` out of
   application, `__DEV__` replaced by an injected error hook.
4. Routes implemented on core: Postgres repositories (Drizzle), a per-user outbox, auth. Tests on
   PGlite.
5. Mobile sync client; upload of the existing `admin` history.

## Why

- **Hono:** zero-config on Vercel, small cold starts, `app.request()` tests without a server; h3-js
  (plain JS) runs on Node. Fastify is heavier; a second Next.js app carries a framework for JSON.
- **zod-openapi:** one schema, no hand-written spec to drift; OpenAPI 3.1.
- **Frankfurt + Neon + Better Auth:** EU personal data (GPS tracks) in EU regions, users in our own
  tables, DPAs with Vercel and Neon.
- **Static Swagger on the local site:** the website is a static export; the dev route serves
  swagger-ui-dist and the generated spec, so the public build is unchanged.

Rejected: Next.js route handlers (framework weight, no OpenAPI); hand-written YAML (drifts from
code); Vercel Postgres (retired, now Neon); sharing the SQLite repositories with the server (no
`user_id`, SQLite-only SQL); uploading the phone's turf claims instead of recomputing (two sources
of truth).

## Constraints and risks

- **Vercel limits:** request bodies ≤ 4.5 MB (tracks go compact/gzipped, or chunked), 300 s
  functions on Hobby; Hobby is non-commercial (Pro for launch); pin `regions: ["fra1"]`.
- **Turf determinism:** pin h3-js to one exact version in core; add GPX → cell-set fixture vectors
  beside `turf-vectors.json`.
- **Local time in domain code** (activity default names, week start, time-of-day achievements):
  store an IANA `timeZone` on each Activity before achievements run on a UTC server. (Since
  api-sync-2026-10-20.md achievements stay on the device and the phone always sends a name.)
- **Privacy:** no coordinates in logs, error bodies or OpenAPI examples (examples use public
  landmarks); outbox `last_error` never goes to log drains; the OSRM gap router is not called from
  the server without its own instance and a privacy note.
- **Founder actions later:** Vercel project (Root Directory `apps/api`), Neon project in
  `aws-eu-central-1`, DPAs, auth provider keys.
