# Data flow: create on the phone, manage on the web, adjust in admin

**Status:** decided by the founder on 2026-10-23, not built. Target: **v0.11.0**. v0.10.0 shipped
with today's one-way flow and web portal Slice 0 only; Slice 1 (map and activities, read-only) is
not built yet. Checked 2026-10-23: no phone pull, no web delete, no `/internal/admin` routes
(`apps/api/src/routes/internal.ts` holds only the retention cron).

## Today (v0.10.0)

- The phone owns activities, tracks, Home City and turf (SQLite). It uploads every change to the API
  (after each change, on app start, on returning to the foreground; foreground only).
- The API owns the account (e-mail, name, password, sessions, consents) and holds a copy of the
  phone's data, with every number and the turf recomputed by `@cityturfer/core`.
- The web portal reads the API. Its account actions (sign out, export, delete the account) reach the
  phone; it cannot change activities.
- The admin portal holds staff accounts in its own database and has no access to user data.
- The phone never pulls changes from the server, except a restore on a new phone.

## Decisions

| #   | Question                                     | Decision                                                                                                                                                                                                                                                     |
| --- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| F1  | Where are records created?                   | On the phone only (recording, Apple Health, imports), through the API into the database. Unchanged.                                                                                                                                                          |
| F2  | What happens on the phone after a web delete | **Deleted everywhere.** The phone pulls the delete and removes the activity and its turf, as if deleted on the phone. This replaces decision B4 ("a server-side action never removes phone data") for deletes the user makes themselves on the web.          |
| F3  | What can staff change?                       | **Everything but tracks:** the account (e-mail, name, block, erase), consents, an activity's name, type or deletion, the Home City. Staff never see or edit tracks or turf cells (no coordinates, G9). Every staff action is audited (who, when, what, why). |
| F4  | When?                                        | **v0.11.0**, as one piece: phone pull, web delete, admin routes and their sync tests.                                                                                                                                                                        |

## What it takes (v0.11.0)

1. **Phone pull.** At the moments it uploads, the phone reads `/v1/sync/changes` since its last
   cursor and applies deletes and edits through its own use cases (turf, stats and the outbox stay
   consistent). The sync contract already says "tombstoned → delete it locally"; the phone doesn't
   do it yet.
2. **Conflict rules.** A delete wins over any edit. Edits: the last write wins on the edit's time
   (the API already does this for renames, decision D6). To settle with the API team: a type change
   on the server reclaims turf on both sides. (The server projection already reclaims when an upload
   replaces an activity with another type; `PATCH /v1/activities/{id}` changes only the name today.)
3. **Web delete.** A delete action on the activity pages (Slice 1+), through the existing
   `DELETE /v1/activities/{id}` with the cookie session and the CSRF guard.
4. **Admin routes.** Audited `/internal/admin/v1` routes for F3, staff assertion from apps/admin
   (decision AD3 first). Edits land as normal versioned changes, so the phone and the web pick them
   up the same way.
5. **Sync tests.** New scenarios in `pnpm test:chain`: a web delete reaches the phone (activity and
   turf gone, nothing else touched); an admin rename, type change, delete and erasure reach the
   phone and the web; conflicts resolve by the rules in 2. The admin probe in
   `apps/mobile/src/test-support/chain/admin.ts` fails the day the admin routes exist, so the
   observer gets written.
6. **Privacy policy and copy.** Say that staff can change account and activity details but never see
   routes, and that a web delete removes the activity from the phone too.

## Not decided yet

- Edits other than delete on the web (rename, type): allowed in v0.11.0 or later.
- Several phones on one account editing at once (the pull makes it possible; conflicts as in 2).
- Background sync (a silent push telling a phone to pull): optional; pulling on app open covers most
  cases.
